This page provides a **layered UAT verification matrix** for validating your Client-Side Defense deployment end-to-end. Each test case follows the infrastructure dependency chain — from DNS resolution through CSD telemetry — so you can systematically prove every component is working correctly.

These commands are the **API equivalent** of the [CSD Console Walkthrough](/csd/en/csd-console/) — use them when you need to verify from the terminal, automate monitoring, or demonstrate CSD capabilities without the UI.

## Prerequisites

Set up your environment variables as described in [API Automation &mdash; Environment Setup](/csd/en/demo/#environment-setup):

```bash
set -a && source .env && set +a
```

All commands below use the `<TOKEN>` placeholder format. Substitute with your environment variables (`$XCSH_API_TOKEN`, `$XCSH_NAMESPACE`, etc.) or use the interactive form at the top of the page.

<Aside type="caution">
Choose one ownership mode. Never run the API create/update/delete workflow against resources present in Terraform state.

The commands on this page are read-only observations unless a remediation step explicitly says otherwise. For Terraform-owned resources, remediate in Terraform, review a fresh saved plan, and apply it against the same backend and state. Do not use API mutation as a fallback.

</Aside>

## API Behavior Notes

<Aside type="note">
**PUT and DELETE return empty `\{\}`** on HTTP 200 — this is the expected success response, not an error. Only **POST** returns the created object.

**List endpoints** (e.g., `/healthchecks`) and **individual GET endpoints** (e.g., `/healthchecks/\{name\}`) return different response structures. See [API Reference &mdash; API Conventions](/csd/en/api-reference/#api-conventions) for the correct `jq` paths.

</Aside>

## Time Range Helpers

Many CSD endpoints require epoch timestamps (seconds since Unix epoch). These one-liners compute start/end times for common ranges.

**Cross-platform** (macOS + Linux):

```bash
# Current time as epoch seconds
NOW=$(date +%s)

# 1 hour ago
START_1H=$(( NOW - 3600 ))

# 24 hours ago
START_24H=$(( NOW - 86400 ))

# 7 days ago
START_7D=$(( NOW - 604800 ))

# 30 days ago
START_30D=$(( NOW - 2592000 ))
```

| Preset   | Seconds   | Shell expression               |
| -------- | --------- | ------------------------------ |
| 1 hour   | 3,600     | `$(( $(date +%s) - 3600 ))`    |
| 24 hours | 86,400    | `$(( $(date +%s) - 86400 ))`   |
| 7 days   | 604,800   | `$(( $(date +%s) - 604800 ))`  |
| 30 days  | 2,592,000 | `$(( $(date +%s) - 2592000 ))` |

<Aside type="note">
  CSD endpoints (`/api/shape/csd/`) use **epoch seconds** (e.g., `1710000000`). Access log endpoints (`/api/data/`) use
  **ISO 8601** timestamps (e.g., `2024-03-10T00:00:00Z`). The commands in each section use the correct format for that
  endpoint.
</Aside>

## Test Case Format

Each test below follows this structure:

| Field              | Description                                           |
| ------------------ | ----------------------------------------------------- |
| **Test ID**        | Layer number + sequential ID (e.g., DNS-1, TLS-2)     |
| **What it proves** | The specific infrastructure fact being verified       |
| **Command**        | Ready-to-run `curl` or `dig` command                  |
| **PASS / FAIL**    | Expected output for healthy vs. unhealthy state       |
| **Fix**            | Link to the relevant setup or troubleshooting section |

## Layer 1: DNS Resolution

DNS is the foundation — if the domain does not resolve to the load balancer VIP, nothing else works.

### DNS-1: A Records Match the Current LB VIPs

**What it proves:** Every A record for the exact protected domain resolves to a VIP currently reported by the exact load balancer in the expected namespace.

<div data-xcsh-context="shell" data-xcsh-fields="XCSH_API_URL XCSH_API_TOKEN XCSH_NAMESPACE XCSH_LB_NAME XCSH_DOMAINNAME">

```bash
LB=$(curl -fsS \
  -H "Authorization: APIToken <XCSH_API_TOKEN>" \
  "<XCSH_API_URL>/api/config/namespaces/<XCSH_NAMESPACE>/http_loadbalancers/<XCSH_LB_NAME>")
DNS_A=$(dig +short <XCSH_DOMAINNAME> A | sort -u)
LB_VIPS=$(printf '%s' "$LB" | jq -r '.spec.dns_info[]?.ip_address // empty' | sort -u)

printf '%s' "$LB" | jq -e \
  --arg name "<XCSH_LB_NAME>" \
  --arg namespace "<XCSH_NAMESPACE>" \
  --arg domain "<XCSH_DOMAINNAME>" \
  '.metadata.name == $name and .metadata["namespace"] == $namespace and (.spec.domains | index($domain) != null)' >/dev/null
test -n "$DNS_A"
test "$DNS_A" = "$LB_VIPS"
```

</div>

| Result                                                                                                                          | Meaning                                                                       |
| ------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------- |
| **PASS** &mdash; identity/domain assertion succeeds and the non-empty sorted A-record set exactly equals the current LB VIP set | DNS names the intended LB and no stale or foreign VIP is present              |
| **FAIL** &mdash; identity/domain mismatch, empty set, or unequal sets                                                           | Correct the domain, namespace, LB selection, or DNS records before continuing |

<Aside type="note">

A returned IP by itself is not proof: it must equal the current VIP set on the named LB. If the domain previously returned `NXDOMAIN`, repeat the A query against the authoritative nameserver to distinguish stale recursive cache from authoritative state.

</Aside>

### DNS-2: ACME Challenge Records

**What it proves:** The exact challenge owner has the record type and value required by the selected DNS ownership mode.

<div data-xcsh-context="shell" data-xcsh-fields="XCSH_DOMAINNAME">

```bash
ACME_OWNER="_acme-challenge.<XCSH_DOMAINNAME>"
ACME_CNAME=$(dig +short "$ACME_OWNER" CNAME)
ACME_TXT=$(dig +short "$ACME_OWNER" TXT)
printf 'owner=%s\nCNAME=%s\nTXT=%s\n' "$ACME_OWNER" "$ACME_CNAME" "$ACME_TXT"
```

</div>

| Result                                                                                                                                   | Meaning                              |
| ---------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------ |
| **PASS (external DNS)** &mdash; the exact owner has the configured F5 automatic-certificate CNAME target                                 | External ACME delegation is present  |
| **PASS (F5 Distributed Cloud managed DNS)** &mdash; the exact owner has the platform-managed TXT value and no conflicting external CNAME | Managed ACME validation is present   |
| **FAIL** &mdash; expected value missing, wrong owner, conflicting records, or both empty                                                 | Certificate validation is not proven |

Do not accept any non-empty CNAME or TXT as PASS. Compare the observed value with the value reported for this domain by the current LB certificate metadata or the DNS configuration. For external DNS, create the exact CNAME instructed by that metadata. For managed DNS, enable `allow_http_lb_managed_records` and verify the platform-managed TXT record.

### DNS-3: Nameserver Authority

**What it proves:** Whether F5 XC is the authoritative DNS provider for the root domain.

<div data-xcsh-context="shell" data-xcsh-fields="XCSH_ROOT_DOMAIN">

```bash
dig +short NS <XCSH_ROOT_DOMAIN>
```

</div>

| Result                                                 | Meaning                                               |
| ------------------------------------------------------ | ----------------------------------------------------- |
| Includes `ns1.f5clouddns.com` and `ns2.f5clouddns.com` | F5 XC managed DNS &mdash; records can be auto-created |
| Other nameservers                                      | External DNS &mdash; records must be created manually |

**Fix:** [Phase 1 — DNS, Certificate, and Origin Recovery](/csd/en/demo/phase-1-build/#step-6-dns-certificate-and-origin-recovery)

### DNS-4: F5 XC Managed Records Enabled

**What it proves:** The F5 XC DNS zone allows automatic record creation for load balancers (F5 XC managed DNS only).

<div data-xcsh-context="shell" data-xcsh-fields="XCSH_API_URL XCSH_API_TOKEN XCSH_ROOT_DOMAIN">

```bash
curl -s \
  -H "Authorization: APIToken <XCSH_API_TOKEN>" \
  "<XCSH_API_URL>/api/config/dns/namespaces/system/dns_zones/<XCSH_ROOT_DOMAIN>" \
  | jq '.spec.primary.allow_http_lb_managed_records'
```

</div>

| Result                             | Meaning                                              |
| ---------------------------------- | ---------------------------------------------------- |
| **PASS** &mdash; `true`            | Platform will auto-create A and ACME records for LBs |
| **FAIL** &mdash; `false` or `null` | Managed records disabled; enable via zone update     |

<Aside type="caution">
A `false` result is a common misconfiguration when using F5 XC managed DNS. Without managed records enabled, the platform cannot create the A record pointing to the VIP or the ACME challenge record. The load balancer then remains in `VIRTUAL_HOST_PENDING_A_RECORD` and the certificate remains in `PreDomainChallengePending`.

Enable managed records on the DNS zone or create the records manually.

</Aside>

**Fix:** [Phase 1 — DNS, Certificate, and Origin Recovery](/csd/en/demo/phase-1-build/#step-6-dns-certificate-and-origin-recovery)

## Layer 2: TLS Certificate

The single load balancer named by `XCSH_LB_NAME` terminates HTTPS and redirects HTTP to HTTPS. HTTP is redirect behavior on this object, not a second load balancer or a fallback path.

### TLS-1: Certificate State

**What it proves:** The automatic TLS certificate has been issued on the load balancer.

<div data-xcsh-context="shell" data-xcsh-fields="XCSH_API_URL XCSH_API_TOKEN XCSH_NAMESPACE XCSH_LB_NAME">

```bash
curl -s \
  -H "Authorization: APIToken <XCSH_API_TOKEN>" \
  "<XCSH_API_URL>/api/config/namespaces/<XCSH_NAMESPACE>/http_loadbalancers/<XCSH_LB_NAME>" \
  | jq '.spec.cert_state'
```

</div>

| Result                                                                          | Meaning                                                                                |
| ------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------- |
| **PASS** &mdash; `"CertificateValid"` or `"AutoCertRenewing"`                   | Certificate is valid and active                                                        |
| **WAIT** &mdash; `"DomainChallengePending"` or `"DomainChallengeStarted"`       | ACME challenge is still progressing                                                    |
| **FAIL** &mdash; `"PreDomainChallengePending"` or `"AutoCertDomainRateLimited"` | HTTPS is not ready; resolve the ACME record or rate limit before end-to-end validation |

### TLS-2: Certificate Details

**What it proves:** The certificate metadata and ACME records correspond to the configured domain.

<div data-xcsh-context="shell" data-xcsh-fields="XCSH_API_URL XCSH_API_TOKEN XCSH_NAMESPACE XCSH_LB_NAME">

```bash
curl -s \
  -H "Authorization: APIToken <XCSH_API_TOKEN>" \
  "<XCSH_API_URL>/api/config/namespaces/<XCSH_NAMESPACE>/http_loadbalancers/<XCSH_LB_NAME>" \
  | jq '{
    cert_state: .spec.cert_state,
    auto_cert_info: .spec.auto_cert_info,
    vip_ip: .spec.dns_info[0].ip_address
  }'
```

</div>

### TLS-3: Live TLS Handshake

**What it proves:** A client can complete TLS to the protected domain with a valid certificate.

<div data-xcsh-context="shell" data-xcsh-fields="XCSH_DOMAINNAME">

```bash
curl -sv "https://<XCSH_DOMAINNAME>/" 2>&1 \
  | grep -E 'SSL connection|subject:|expire date:|issuer:'
```

</div>

| Result                                                             | Meaning                                                 |
| ------------------------------------------------------------------ | ------------------------------------------------------- |
| **PASS** &mdash; TLS connection, expected subject, and valid dates | Client-to-F5 XC TLS is ready                            |
| **FAIL** &mdash; connection or certificate error                   | Check DNS, LB virtual-host state, and certificate state |

## Layer 3: HTTP Load Balancer

All checks in this layer read the same unsuffixed load balancer object.

### LB-1: Operational State

**What it proves:** The virtual host is deployed and ready.

<div data-xcsh-context="shell" data-xcsh-fields="XCSH_API_URL XCSH_API_TOKEN XCSH_NAMESPACE XCSH_LB_NAME">

```bash
curl -s \
  -H "Authorization: APIToken <XCSH_API_TOKEN>" \
  "<XCSH_API_URL>/api/config/namespaces/<XCSH_NAMESPACE>/http_loadbalancers/<XCSH_LB_NAME>" \
  | jq '.spec.state'
```

</div>

| Result                                  | Meaning                                                        |
| --------------------------------------- | -------------------------------------------------------------- |
| **PASS** &mdash; `"VIRTUAL_HOST_READY"` | LB virtual host is operational                                 |
| **FAIL** &mdash; pending state          | Inspect DNS, certificate state, and virtual-host error details |

### LB-2: Domain and HTTPS Redirect Configuration

**What it proves:** The LB serves the expected domain with automatic HTTPS and HTTP redirect enabled.

<div data-xcsh-context="shell" data-xcsh-fields="XCSH_API_URL XCSH_API_TOKEN XCSH_NAMESPACE XCSH_LB_NAME">

```bash
curl -s \
  -H "Authorization: APIToken <XCSH_API_TOKEN>" \
  "<XCSH_API_URL>/api/config/namespaces/<XCSH_NAMESPACE>/http_loadbalancers/<XCSH_LB_NAME>" \
  | jq '{domains: .spec.domains, https_auto_cert: .spec.https_auto_cert, http_redirect: .spec.https_auto_cert.http_redirect}'
```

</div>

| Result                                                     | Meaning                                       |
| ---------------------------------------------------------- | --------------------------------------------- |
| **PASS** &mdash; expected domain and `http_redirect: true` | One LB owns HTTPS and redirects HTTP          |
| **FAIL** &mdash; missing domain, HTTPS, or redirect        | Remediate through the selected ownership mode |

### LB-3: CSD Enabled on LB

**What it proves:** Client-Side Defense injects JavaScript on all pages.

<div data-xcsh-context="shell" data-xcsh-fields="XCSH_API_URL XCSH_API_TOKEN XCSH_NAMESPACE XCSH_LB_NAME">

```bash
curl -s \
  -H "Authorization: APIToken <XCSH_API_TOKEN>" \
  "<XCSH_API_URL>/api/config/namespaces/<XCSH_NAMESPACE>/http_loadbalancers/<XCSH_LB_NAME>" \
  | jq '{
    csd_enabled: (if .spec.client_side_defense then true else false end),
    js_policy: .spec.client_side_defense.policy
  }'
```

</div>

| Result                                                          | Meaning                                       |
| --------------------------------------------------------------- | --------------------------------------------- |
| **PASS** &mdash; `csd_enabled: true` with `js_insert_all_pages` | CSD injection is configured for all pages     |
| **FAIL** &mdash; absent CSD configuration                       | Remediate through the selected ownership mode |

### LB-4: Default Route Pool

**What it proves:** The LB references the expected origin pool.

<div data-xcsh-context="shell" data-xcsh-fields="XCSH_API_URL XCSH_API_TOKEN XCSH_NAMESPACE XCSH_LB_NAME">

```bash
curl -s \
  -H "Authorization: APIToken <XCSH_API_TOKEN>" \
  "<XCSH_API_URL>/api/config/namespaces/<XCSH_NAMESPACE>/http_loadbalancers/<XCSH_LB_NAME>" \
  | jq '.spec.default_route_pools[] | {pool: .pool.name, namespace: .pool.namespace, weight, priority}'
```

</div>

### LB-5: Deployment Status

**What it proves:** The virtual host, VIP, certificate, and route configuration are reported by the same LB object.

<div data-xcsh-context="shell" data-xcsh-fields="XCSH_API_URL XCSH_API_TOKEN XCSH_NAMESPACE XCSH_LB_NAME">

```bash
curl -s \
  -H "Authorization: APIToken <XCSH_API_TOKEN>" \
  "<XCSH_API_URL>/api/config/namespaces/<XCSH_NAMESPACE>/http_loadbalancers/<XCSH_LB_NAME>" \
  | jq '{
    name: .metadata.name,
    state: .spec.state,
    cert_state: .spec.cert_state,
    domains: .spec.domains,
    dns_info: .spec.dns_info,
    http_redirect: .spec.https_auto_cert.http_redirect,
    csd_enabled: (if .spec.client_side_defense then true else false end),
    route_pools: [.spec.default_route_pools[] | .pool.name],
    virtual_host_errors: [.status[]? | select(.virtual_host_status != null) | .virtual_host_status | {state, error_description, suggested_action}]
  }'
```

</div>

## Layer 4: Origin Pool

The origin pool supports either an AWS ALB hostname (`public_name`) or an Azure/public lab IP (`public_ip`). Set `XCSH_ORIGIN_KIND` to `public_name` or `public_ip`; set the matching `XCSH_ORIGIN_HOSTNAME` or `XCSH_ORIGIN_IP` variable.

### OP-1: Origin Pool Configuration

**What it proves:** The configured oneOf origin kind and value match the intended backend.

<div data-xcsh-context="shell" data-xcsh-fields="XCSH_API_URL XCSH_API_TOKEN XCSH_NAMESPACE XCSH_ORIGIN_POOL_NAME XCSH_ORIGIN_KIND XCSH_ORIGIN_HOSTNAME XCSH_ORIGIN_IP">

```bash
ORIGIN_POOL=$(curl -s \
  -H "Authorization: APIToken <XCSH_API_TOKEN>" \
  "<XCSH_API_URL>/api/config/namespaces/<XCSH_NAMESPACE>/origin_pools/<XCSH_ORIGIN_POOL_NAME>")

case "<XCSH_ORIGIN_KIND>" in
  public_name)
    echo "$ORIGIN_POOL" | jq --arg expected "<XCSH_ORIGIN_HOSTNAME>" '{
      name: .metadata.name,
      origin_kind: "public_name",
      origin: [.spec.origin_servers[] | .public_name.dns_name],
      expected: $expected,
      port: .spec.port
    }'
    ;;
  public_ip)
    echo "$ORIGIN_POOL" | jq --arg expected "<XCSH_ORIGIN_IP>" '{
      name: .metadata.name,
      origin_kind: "public_ip",
      origin: [.spec.origin_servers[] | .public_ip.ip],
      expected: $expected,
      port: .spec.port
    }'
    ;;
  *) echo "FAIL: XCSH_ORIGIN_KIND must be public_name or public_ip" >&2; exit 1 ;;
esac
```

</div>

| Result                                                                                        | Meaning                                              |
| --------------------------------------------------------------------------------------------- | ---------------------------------------------------- |
| **PASS** &mdash; `origin` contains the matching expected hostname or IP and the expected port | Origin pool oneOf choice is correct                  |
| **FAIL** &mdash; wrong kind, value, or port                                                   | Remediate the origin pool through its selected owner |

### OP-2: TLS to Origin

```bash
echo "$ORIGIN_POOL" | jq '{
  tls_config: (if .spec.no_tls then "no_tls (plaintext)" elif .spec.use_tls then "use_tls (encrypted)" else "unknown" end)
}'
```

### OP-3: Healthcheck Association

```bash
echo "$ORIGIN_POOL" | jq '.spec.healthcheck'
```

An empty array is valid when no optional healthcheck was selected.

### OP-4: Direct Origin Observation

**What it proves:** The origin responds from the operator's current network. It does not prove F5 XC-to-origin health.

<div data-xcsh-context="shell" data-xcsh-fields="XCSH_ORIGIN_KIND XCSH_ORIGIN_HOSTNAME XCSH_ORIGIN_IP XCSH_ORIGIN_PORT">

```bash
case "<XCSH_ORIGIN_KIND>" in
  public_name) ORIGIN_URL="http://<XCSH_ORIGIN_HOSTNAME>:<XCSH_ORIGIN_PORT>/" ;;
  public_ip)   ORIGIN_URL="http://<XCSH_ORIGIN_IP>:<XCSH_ORIGIN_PORT>/" ;;
  *) echo "FAIL: invalid XCSH_ORIGIN_KIND" >&2; exit 1 ;;
esac

curl -sS -o /dev/null -w '%{http_code}\n' "$ORIGIN_URL"
```

</div>

<Aside type="note">
  A successful direct request proves only client-to-origin reachability. F5 XC may use a different path, source address,
  DNS resolver, or policy. Use LB access logs and the protected HTTPS request to prove the F5 XC-to-origin path.
</Aside>

## Layer 5: Health Check

Health checks monitor backend availability. They are optional for CSD but useful for production deployments.

### HC-1: Healthcheck Configuration

**What it proves:** The healthcheck exists with the correct type, path, timing, and thresholds.

<div data-xcsh-context="shell" data-xcsh-fields="XCSH_API_URL XCSH_API_TOKEN XCSH_NAMESPACE XCSH_HC_NAME">

```bash
curl -s \
  -H "Authorization: APIToken <XCSH_API_TOKEN>" \
  "<XCSH_API_URL>/api/config/namespaces/<XCSH_NAMESPACE>/healthchecks/<XCSH_HC_NAME>" \
  | jq '{
    name: .metadata.name,
    type: (if .spec.http_health_check then "HTTP" elif .spec.tcp_health_check then "TCP" else "unknown" end),
    path: .spec.http_health_check.path,
    expected_status: .spec.http_health_check.expected_status_codes,
    timeout: .spec.timeout,
    interval: .spec.interval,
    unhealthy_threshold: .spec.unhealthy_threshold,
    healthy_threshold: .spec.healthy_threshold
  }'
```

</div>

| Result                                                            | Meaning                                                                                                                                         |
| ----------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------- |
| **PASS** &mdash; shows HTTP type with path `/` and expected `200` | Healthcheck configured correctly                                                                                                                |
| **FAIL** &mdash; `404` response                                   | Healthcheck does not exist (it may have been omitted; see [Phase 1 Step 3](/csd/en/demo/phase-1-build/#step-3-optionally-create-a-healthcheck)) |

### HC-2: List All Healthchecks

**What it proves:** Enumerates all healthchecks in the namespace to verify naming and count.

<div data-xcsh-context="shell" data-xcsh-fields="XCSH_API_URL XCSH_API_TOKEN XCSH_NAMESPACE">

```bash
curl -s \
  -H "Authorization: APIToken <XCSH_API_TOKEN>" \
  "<XCSH_API_URL>/api/config/namespaces/<XCSH_NAMESPACE>/healthchecks" \
  | jq -r '
    ["NAME", "NAMESPACE", "DESCRIPTION"],
    (.items[] | [
      .name,
      .namespace,
      (.description | if length == 0 then "—" else . end)
    ])
    | @tsv' | column -t
```

</div>

<Aside type="note">
  The list endpoint returns summary data only (name, namespace, description). To see full configuration details (type,
  path, interval, timeout), query an individual healthcheck using [HC-1](#hc-1-healthcheck-configuration).
</Aside>

## Layer 6: CSD Configuration

CSD must be enabled at the tenant level and have the JavaScript injection tag configured.

### CSD-1: Tenant CSD Status

**What it proves:** CSD is configured and enabled for the tenant.

<div data-xcsh-context="shell" data-xcsh-fields="XCSH_API_URL XCSH_API_TOKEN XCSH_NAMESPACE">

```bash
curl -s \
  -H "Authorization: APIToken <XCSH_API_TOKEN>" \
  "<XCSH_API_URL>/api/shape/csd/namespaces/<XCSH_NAMESPACE>/status" \
  | jq '{isConfigured, isEnabled}'
```

</div>

| Result                                 | Meaning                                                             |
| -------------------------------------- | ------------------------------------------------------------------- |
| **PASS** &mdash; both `true`           | CSD is active for this tenant                                       |
| **FAIL** &mdash; `isConfigured: false` | CSD not enabled at tenant level &mdash; contact F5 XC administrator |
| **FAIL** &mdash; `isEnabled: false`    | CSD configured but not active                                       |

### CSD-2: JS Injection Tag

**What it proves:** The CSD JavaScript injection tag is generated and ready for injection.

<div data-xcsh-context="shell" data-xcsh-fields="XCSH_API_URL XCSH_API_TOKEN XCSH_NAMESPACE">

```bash
curl -s \
  -H "Authorization: APIToken <XCSH_API_TOKEN>" \
  "<XCSH_API_URL>/api/shape/csd/namespaces/<XCSH_NAMESPACE>/js_configuration" \
  | jq '{has_script_tag: (.scriptTag | length > 0)}'
```

</div>

| Result                                   | Meaning                                                                          |
| ---------------------------------------- | -------------------------------------------------------------------------------- |
| **PASS** &mdash; `has_script_tag: true`  | JS injection tag is configured                                                   |
| **FAIL** &mdash; `has_script_tag: false` | No script tag &mdash; verify CSD is enabled and a protected domain is registered |

### CSD-3: JS Tag Content

**What it proves:** Shows the full script tag for verification or manual injection.

```bash
  "<XCSH_API_URL>/api/shape/csd/namespaces/<XCSH_NAMESPACE>/js_configuration" \
  | jq '.scriptTag'
```

</div>

### CSD-4: Protected Domain Registration

**What it proves:** The exact protected-domain name and namespace match the expected application.

<div data-xcsh-context="shell" data-xcsh-fields="XCSH_API_URL XCSH_API_TOKEN XCSH_NAMESPACE XCSH_DOMAINNAME">

```bash
curl -s \
  -H "Authorization: APIToken <XCSH_API_TOKEN>" \
  "<XCSH_API_URL>/api/shape/csd/namespaces/<XCSH_NAMESPACE>/protected_domains" \
  | jq -e --arg name "<XCSH_DOMAINNAME>" --arg namespace "<XCSH_NAMESPACE>" \
    '.items[] | select(.name == $name and .["namespace"] == $namespace) | {name, namespace, description}'
```

</div>

| Result                                                                               | Meaning                                                                             |
| ------------------------------------------------------------------------------------ | ----------------------------------------------------------------------------------- |
| **PASS** &mdash; an item exactly matches both `XCSH_DOMAINNAME` and `XCSH_NAMESPACE` | The intended domain is registered in the intended namespace                         |
| **FAIL** &mdash; no exact match                                                      | A different or merely non-empty item does not prove protection for this application |

### CSD-5: Live Application and JS Injection Verification

**What it proves:** The protected HTTPS response is the expected scenario application and contains the injected CSD path. `XCSH_CSD_DEPLOYMENT_MODE` selects ownership (`api` or `terraform`) only; it never selects AWS or Azure evidence.

<div data-xcsh-context="shell" data-xcsh-fields="XCSH_CSD_DEPLOYMENT_MODE XCSH_DOMAINNAME XCSH_APPLICATION_MARKER">

```bash
case "<XCSH_CSD_DEPLOYMENT_MODE>" in
  api|terraform) ;;
  *) echo "FAIL: XCSH_CSD_DEPLOYMENT_MODE must be api or terraform" >&2; exit 1 ;;
esac

APPLICATION_MARKER='<XCSH_APPLICATION_MARKER>'
test -n "$APPLICATION_MARKER" || { echo "FAIL: XCSH_APPLICATION_MARKER is required for every scenario" >&2; exit 1; }
case "$APPLICATION_MARKER" in
  'replace-with-application-marker'|'replace-with-azure-application-marker'|'<XCSH_APPLICATION_MARKER>')
    echo "FAIL: replace the XCSH_APPLICATION_MARKER documentation placeholder" >&2
    exit 1
    ;;
esac

APPLICATION_HTML=$(curl -fsS "https://<XCSH_DOMAINNAME>/")
printf '%s' "$APPLICATION_HTML" | grep -Fqi "$APPLICATION_MARKER" \
  && echo "PASS: expected application rendered" \
  || { echo "FAIL: expected application marker missing" >&2; exit 1; }
printf '%s' "$APPLICATION_HTML" | grep -q '__imp_apg__' \
  && echo "PASS: __imp_apg__ injected" \
  || { echo "FAIL: __imp_apg__ missing" >&2; exit 1; }
```

</div>

Both assertions must succeed. `XCSH_APPLICATION_MARKER` always identifies the expected
application/scenario independently of `XCSH_ORIGIN_KIND`. The repository reference defaults to
`OWASP Juice Shop`; every non-reference API or Azure scenario must supply its own stable,
deployment-specific marker. Empty and documentation-placeholder values fail closed.
`XCSH_CSD_DEPLOYMENT_MODE` continues to identify ownership only.

An HTTPS status alone does not identify the intended origin, and direct-origin reachability does not prove the F5 path.

### TV-1: Request Count (Last 24 Hours)

**What it proves:** Traffic is reaching the load balancer. Zero results means no traffic is arriving.

<div data-xcsh-context="shell" data-xcsh-fields="XCSH_API_URL XCSH_API_TOKEN XCSH_NAMESPACE">

```bash

    "start_time": "'"$(date -u -d '24 hours ago' +%Y-%m-%dT%H:%M:%SZ 2>/dev/null || date -u -v-24H +%Y-%m-%dT%H:%M:%SZ)"'",
    "end_time": "'"$(date -u +%Y-%m-%dT%H:%M:%SZ)"'"
  }' \
  "<XCSH_API_URL>/api/data/namespaces/<XCSH_NAMESPACE>/access_logs/aggregation" \
  | jq '{total_requests: .total_hits}'
```

</div>

| Result                                                                 | Meaning                                                                                                                          |
| ---------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------- |
| **PASS** &mdash; `total_requests` is a non-zero string (e.g., `"380"`) | Traffic is flowing through the LB                                                                                                |
| **FAIL** &mdash; `"0"` or no data                                      | No traffic reaching the LB &mdash; check [DNS-1](#dns-1-a-records-match-the-current-lb-vips) and [LB-1](#lb-1-operational-state) |

<Aside type="note">
  The `total_hits` value is returned as a **string** (e.g., `"380"`), not an integer. The namespace is inferred from the
  URL path &mdash; do not include it in the request body.
</Aside>

### TV-2: Status Code Distribution

**What it proves:** The breakdown of response status codes reveals error patterns.

<div data-xcsh-context="shell" data-xcsh-fields="XCSH_API_URL XCSH_API_TOKEN XCSH_NAMESPACE">

```bash
curl -s -X POST \
  -H "Authorization: APIToken <XCSH_API_TOKEN>" \
  -H "Content-Type: application/json" \
  -d '{
    "start_time": "'"$(date -u -d '24 hours ago' +%Y-%m-%dT%H:%M:%SZ 2>/dev/null || date -u -v-24H +%Y-%m-%dT%H:%M:%SZ)"'",
    "end_time": "'"$(date -u +%Y-%m-%dT%H:%M:%SZ)"'",
    "sort": "DESCENDING",
    "limit": 100
  }' \
  "<XCSH_API_URL>/api/data/namespaces/<XCSH_NAMESPACE>/access_logs" \
  | jq -r '
    [.logs[] | fromjson | .rsp_code_class]
    | group_by(.) | map({class: .[0], count: length})
    | sort_by(-.count)
    | ["STATUS_CLASS", "COUNT"], (.[] | [.class, .count])
    | @tsv' | column -t
```

</div>

<Aside type="note">
  The aggregation endpoint does not support `terms` bucketing &mdash; `aggs` always returns empty. This command fetches
  the most recent 100 log entries and computes the distribution client-side. Each log entry is a **JSON string** that
  must be parsed with `fromjson`.
</Aside>

Expected output for a healthy site:

```text
STATUS_CLASS                  COUNT
2xx                           82
downstream_remote_disconnect  18
```

| Result                            | Meaning                                          |
| --------------------------------- | ------------------------------------------------ |
| **PASS** &mdash; majority `2xx`   | Site is serving successful responses             |
| **WARN** &mdash; high `4xx` count | Client errors (bad URLs, missing resources)      |
| **FAIL** &mdash; high `5xx` count | Server errors &mdash; check origin server health |

The `downstream_remote_disconnect` class indicates the client closed the connection before the response completed (common for long-polling or WebSocket upgrade requests).

**What it proves:** A recent request for the protected domain was recorded after the validation request.

### Managed Records Disabled on DNS Zone

[About Client-Side Defense](https://docs.cloud.f5.com/docs-v2/client-side-defense/concepts/about-csd) and
[Configure Client-Side Defense](https://docs.cloud.f5.com/docs-v2/client-side-defense/how-tos/configure-csd).

Historical evidence must be interpreted narrowly. On 2026-09-23, a tenant
`ClientSideDefenseHttpHeaderModified` record named `x-content-type-options`, `x-frame-options`, and
`cache-control`, reported `modification=Added`, and included the exact protected path `/`. It proves
detection for that event, not the Compromised semantic or an official monitored-header list. The
2026-09-24 six-header global-value campaign is **INVALID TEST** for Compromised-trigger conclusions:
it had no controlled baseline/comparison cohorts and alert review initially searched current alerts
rather than history. Its later bounded negative search remains an observation, not proof of
unsupported coverage.

Issue #1241 owns the dedicated endpoint and deterministic controller. Use the permanent but
inert-by-default `/csd-page-tamper/payment` endpoint; do not mutate the F5 Distributed Cloud load
balancer or origin pool for an experiment.

`terraform-tfstate-xc`, key `f5-sales-demo/traffic-generator-aws.tfstate`, region `us-east-1`,
then resolves `terraform output -raw instance_id`. Do not pass a worker instance ID. The worker

and status omit worker/account/profile IDs, hostnames and PIDs. A new canary's **local-only,

and requires it to match that binding. `status` needs only the receipt directory.

1. **Bootstrap the control baseline.** Require no Terraform drift, a ready load balancer, a valid certificate, healthy ordinary application traffic, and a healthy dedicated endpoint. From workstation and worker fresh browsers, prove HTTP `200`, all 12 exact candidate headers, all five empty synthetic fields, CSD injection, and a `dip` POST.
   Run control-only traffic for 45 minutes while polling both current alerts and alert history. If deployment creates a correlated Modified/Added alert, wait for resolution and then require a 15-minute quiet period.
2. **Reinforce control for 15 minutes.** Run 12 fresh profiles against the exact payment path without the selector. Every response must retain all 12 exact headers, CSD injection, and `dip` evidence.
3. **Run one mixed cohort for up to 45 minutes.** Alternate fresh control profiles with tampered profiles at the identical URL. Only tampered profiles send `X-CSD-Page-Tamper: <header-id>`. Require the selected header absent, the other 11 exact, and at least 20 complete pairs unless the exact required alert arrives sooner.
4. **Poll current and history every 60 seconds.** Parse JSON-string history entries. Correlate only records whose raw fields match the exact namespace, selected header case-insensitively, path `/csd-page-tamper/payment`, and experiment start window.

5. **Classify conservatively.** Use `COMPROMISED` only for an exact Compromised correlation; `MODIFIED_ONLY` for an exact Modified correlation without Compromised; `NO_ALERT_WITHIN_WINDOW` only when the complete evidence chain is valid but neither arrives; and `INVALID_TEST` for any baseline, cohort, telemetry, overlap, correlation, recovery, cleanup, readiness, or drift failure.

Only then may another header start.

Publish only sanitized receipts and measured outcomes. Until an executed case satisfies every gate, the

The command arms and verifies an owned persistent restoration timer **before** disabling/draining
`csd-continuous.timer` and its service. It snapshots enabled and active states independently.
A worker ownership lock prevents overlapping reservations. The timer remains disabled during
the full baseline, quiet period, reinforcement, XCTO window and recovery. The default guard
budget is 256 minutes: 45-minute baseline, up to 31 minutes quiet handling, 90-minute case
deadline, two 15-minute recovery allowances and 60-minute command/cleanup margin. These are
bounded test windows, not an F5 SLA. No timing shortcut is exposed by this CLI.

Every fresh probe owns a separate Xvfb display and Chrome profile, with no headless argument.
Linux process argv/environment and CDP browser arguments/product must prove the mode before
the document visit. Receipts retain sanitized mode/placement/product and verification booleans,
not raw arguments, display identifiers, process IDs, endpoint bodies or tokens. Failed proof is
`INVALID_TEST`. Only `runDocumentProbe` supplies document and instrumentation evidence.

Normal completion and abort restore the original durable enabled/disabled/static policy and
timer dispatch state, then clean owned units, profiles and processes. A disabled-but-active timer
returns to **disabled and active**, not enabled. Service `Type` and `RemainAfterExit` determine
execution semantics: a timer-dispatched oneshot can transiently be `activating`, finish `inactive`,
or be `active`; these are not durable enablement states. The pre-pause snapshot still rejects
an already `activating` service. Recovery persists progress **before** resuming the timer and
does not stop or restart the dispatcher again on cleanup or persistence retries.

Controller SIGKILL does not cancel the external deadline; worker reboot removes the runtime
boot-trigger suppression and activates persistent restoration. The guard stops only run-owned
probe units during draining. Its original `state.json`, `guard.py`, ownership file and authority
directories are root-owned and private (`0700`); probe profiles and processes belong to `ubuntu`,
which cannot rewrite the restoration authority.

The shared guard/cleanup mutex is a **root-owned empty regular singleton, mode `0600`**,
opened without following symlinks under a canonical root-private `0700` parent. Recovery
holds a nonblocking exclusive descriptor flock and compares descriptor/path inodes. Only an
empty root-owned single-link historical `0644` mutex is repaired, while holding that verified
descriptor; its inode is preserved. Executable `0700` mutexes, writable modes, foreign owners,
symlinks, hardlinks and unsafe parents are rejected without chmod/unlink. Guard scripts remain
`0700`. A held mutex is never replaced or unlinked.

Worker unavailability delays restoration until it returns; permanent disk loss, broken systemd,
changed service definitions or unavailable permissions cannot be guaranteed. Unverified restoration
or cleanup retains the controller lock and fails rather than reporting success. There is no manual
dispatcher restart requirement. An interrupted experiment remains invalid evidence even after
automatic restoration.


With no lock, this command returns a successful no-op without contacting the deployment or
starting traffic. For an interrupted canary, it verifies the original worker/run ownership,
restores dispatch and verifies owned cleanup, then stops. It never starts a fresh worker,
reservation, baseline or canary. Keep `active.lock` until restoration, cleanup and recovery
evidence persistence are verified; do not unlink it to bypass a failure.

New canaries fsync their local run/worker-bound phase before preparation and arm attempts.
Before worker preparation, the independent helper durably records
`/var/lib/xcsh-csd-recovery/<RUN_ID>/lifecycle.json` (`xcsh-csd-prearm-v1`).
`recover-only` permits prearm rollback only with this exact worker binding, `NOT_ARMED`
(or its durable cleanup replay phases), no pause intent, and fresh mutex-held absence checks
for reservation authority, owner, guard/probe units and run processes. It deletes only the
recorded inode-owned worker root; replay retains journal authority outside that root.
Non-canary interrupted recovery never reinitializes the original journal. It first verifies
original inode-owned cleanup, persists a distinct recovery-worker identity in the local lock,
and creates new root-private authority bound to the retained original identity, inode and
cleanup intent. A second interruption cleans that recorded recovery worker before another
fresh recovery workspace is prepared; original dispatch state is never reconstructed.

The worker root and source modules remain root-owned; only individual probe workspaces are
owned by `ubuntu`. Privileged installs use root-private staging, no-follow directory/file
descriptors and inode-bound workspace preparation.
The parent remains root-owned `0755`: `ubuntu` stops its own browser and removes only probe
children. After child-unit completion/cleanup, the privileged controller removes the exact
journal-bound probe and root-installed payload using no-follow descriptors and recorded
inodes. Long commands use bounded root-private staging rather than exceeding SSM limits.
`XCSH_CSD_NONROOT_PROBE=1 XCSH_CSD_FIXTURE_TARGET='data:text/html,<title>isolated-fixture</title>'`
runs the headed source fixture without visiting the payment endpoint. This proves browser
launch/provenance and cleanup only, not CSD instrumentation or efficacy; the production
target default is unchanged.
Both armed restoration and prearm rollback
use the same recorded-inode cleanup: a root-private quarantine under `/tmp` keeps rename on
the worker filesystem even when `/var/lib` is on another mount. Unknown legacy roots are not
deleted. Quarantine authority remains durably recorded for replay.
It performs no probe, target control or restoration and reports `restored: false`,
`required: false`, efficacy **NOT_TESTED**. A failed arm response alone is not proof.
Worker `ARM_INTENT` is durable before snapshot/owner/guard creation; `PAUSE_INTENT`
precedes dispatcher changes. Armed or uncertain phases require the original restoration
authority unchanged. A crash between root creation and inode journaling fails closed rather

and final removal reject foreign run/worker bindings or replacement inodes. Recovery rereads
the authoritative lock after claiming it. Receipts fsync the file and directory before owned
lock removal, and lock removal fsyncs the directory. Terminal recovery failures release only
their verified claim, retaining the experiment lock for immediate retry. Preexisting incomplete
claims or legacy directory gates with unknown ownership remain blocked; they are never
silently deleted or reconstructed.

guard's `state.json` — cannot be reconstructed from the currently blocked runtime. Missing guard
authority is likewise not permission to replace it. Only **preexisting**, root-owned, private,
authoritative evidence from an independent verifier can support absent-state recovery. Do not

### Bounded selector-scope diagnostics (usage)

These commands attach to an independently owned, non-root, headed Chrome with its sandbox

[security-header monitoring process](https://docs.cloud.f5.com/docs-v2/client-side-defense/how-tos/configure-csd#configure-csd-alerts)
describes server header collection, different end users and sequential moving-baseline cycles.
It does not specify a session threshold, processing SLA or headed/Xvfb requirement.

**First prerequisite:** reconcile the current protected-domain UI/API discrepancy in
[#1296](https://github.com/f5-sales-demo/csd/issues/1296) and establish effective registration
before further header trials. Do not increase traffic to compensate for unknown registration.

1. **Collector attribution and reads:** which request and caller supply the persisted header
   baseline? Does the observed same-path `HEAD` belong to that collector, and why is it canceled
   after HTTP `200`? What proves that its wire-visible headers were actually read or persisted?
   The new trace shows tampered headers on this `HEAD`; it does not identify the collector.
2. **Payload acceptance:** what support-approved diagnostic proves header-bearing transport and
   semantic/schema acceptance? October 5 scoped DIP requests were selector-free and finished
   without observed preflight; that removes the earlier wire-selector confounder, not the need
   for decoder/acceptance proof. The October 4 session-wide POST/preflight remains separate.
3. **Eligibility and cycles:** what evidence proves eligible distinct end users, persisted baseline
   and subsequent completed comparisons? Fresh contexts from the same worker/egress do not prove
   distinct end users; 20 mixed pairs do not establish a documented population threshold.
4. **Watched headers and classification:** is XCTO omission eligible in this tenant/path and
   entitlement? Which headers are required or monitored, and which exact alert fields distinguish
   Modified from Compromised, addition from omission, and host/path/header attribution?
5. **Next controlled test:** obtain engineering confirmation of collection/acceptance and a
   support-approved change with observable cycle/eligibility criteria before authorizing another
   bounded single-header test. Do not extend the matrix, repeat the two-hour campaign or increase
   volume blindly. No further test is authorized by this record.
